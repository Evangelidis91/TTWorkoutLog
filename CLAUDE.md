## Architecture

Android workout logging app built with Kotlin and Jetpack Compose following Clean Architecture with MVVM.

### Layer Structure

```
com.evangelidisapps.ttworkoutlog/
├── data/
│   ├── local/          # Room database (entities, DAO, database)
│   ├── model/          # Domain models
│   ├── remote/         # FirestoreRepository (cloud storage)
│   └── repository/     # WorkoutRepository + UserPreferencesRepository
├── ui/
│   ├── auth/           # Authentication (AuthScreen, AuthViewModel)
│   ├── home/           # Main screens (Home, WorkoutDetail, WorkoutEdit, Settings, BodyMeasurements)
│   └── theme/          # Material 3 theming
└── navigation/         # Navigation Compose routes
```

### Data Flow

- **ViewModels** expose UI state via `StateFlow` with `WhileSubscribed(5_000)` sharing strategy
- **WorkoutRepository** maps between Room entities and domain models; abstracts all DB access and delegates cloud writes to `FirestoreRepository`
- **UserPreferencesRepository** wraps DataStore for onboarding/guest state and default style preference
- All database operations use suspend functions and Kotlin Coroutines; queries return `Flow`

### Database Schema

```
WorkoutEntity (workouts)
  └── WorkoutExerciseEntity (workout_exercises) — via workoutId
        ├── ExerciseEntity (exercises)           — via exerciseId (shared exercise catalog)
        └── WorkoutSetEntity (workout_sets)      — via workoutExerciseId
```

`WorkoutRelations.kt` defines the `@Relation` mappings (`WorkoutExerciseWithSetsEntity`, `WorkoutWithDetailsEntity`) used for nested Room queries.

The DAO's `upsertWorkoutWithDetails()` is a `@Transaction` method that atomically writes all four tables. `WorkoutDatabase` uses `fallbackToDestructiveMigration()` — schema changes will wipe data in development.

`WorkoutSetEntity` has a `setType: String = "strength"` field for future exercise type support.

### Storage Strategy: Guest vs Logged-In

- **Guest users**: data stored in Room only. `UserPreferencesRepository` persists `IS_GUEST=true`.
- **Logged-in users**: `WorkoutRepository.upsertWithDetails()` writes to both Room and Firestore. Firestore path: `users/{uid}/workouts/{workoutId}`.
- **On login**: `AuthViewModel.onSignInSuccess()` runs a three-step migration: upload local Room data to Firestore → delete all local data → re-fetch from Firestore into Room.

`FirestoreRepository` serializes `WorkoutWithDetails` manually (no Gson/Moshi) as flat Firestore documents with nested exercise/set arrays. It is a no-op when no user is signed in.

### Authentication Flow

`AuthViewModel` supports email/password, Google Sign-In, and Facebook Login via Firebase Auth, plus a guest path.

On init it reads `HAS_COMPLETED_ONBOARDING` and `IS_GUEST` from DataStore, then checks `Firebase.auth.currentUser` to decide whether to show `auth` or `home`.

`R.string.default_web_client_id` is auto-generated by the Google Services Gradle plugin — it only exists if Google Sign-In is enabled in Firebase Console and `google-services.json` contains an OAuth web client. Without it, Google Sign-In will fail at runtime but the app still builds (placeholder in `strings.xml`).

### WorkoutEditViewModel State

The edit screen uses nested state classes to represent a mutable in-progress workout:

```
WorkoutEditState
  └── List<EditableExerciseState>
        └── List<EditableSetState>
```

On load it fetches the full `WorkoutWithDetails` from the repository and converts it into these mutable UI states. On save it converts back to domain models and calls `repository.upsertWithDetails()`. New workouts default to the style set in `UserPreferencesRepository.defaultStyle`.

### Settings

`SettingsScreen` is backed by `SettingsViewModel` (separate from `HomeViewModel`). It persists a default workout style via `UserPreferencesRepository` (`DEFAULT_STYLE` DataStore key, defaults to `"Standard"`). The `StyleDropdown` composable (defined in `WorkoutEditScreen.kt`, `public`) is shared between the edit and settings screens. Style options: Standard, WOD, For Time, AMRAP, Complex, Other.

### Navigation Routes

Defined in `WorkoutNavGraph.kt`:
- `auth` — Authentication screen
- `home` — Workout list
- `workout/{workoutId}` — Workout detail view
- `workout_edit?workoutId={id}` — Create/edit workout (optional id)
- `settings` — Settings
- `body` — Body measurements
